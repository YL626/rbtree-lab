The memory cost of the parent pointer (HW2 Mutation 3): our O(1)-space `rb_foreach` walks parent pointers, so the spec asks what that pointer costs. There are three different numbers here, and they shouldn't be confused. The structure size is the first one: measured with `sizeof` on this toolchain (gcc 15.2, x86-64), `struct rb_node` is 48 bytes with the parent pointer and 40 bytes without it. The pool stride is the second: the pool rounds every slot up to `alignof(max_align_t)`, which is 16 bytes here, so both 48 and 40 round to the same 48-byte stride, and a 4096-byte slab holds 85 nodes either way (measured with `rb_pool_geometry`). In pooled mode the parent pointer therefore costs nothing extra right now, but that is an accident of the current layout and alignment, not something the design guarantees. The third number is the heap allocation size, which depends on the allocator implementation rather than on our code: in ordinary mode each node is its own `malloc`, and glibc 2.43 reported a usable size of 56 bytes for the 48-byte node and 40 bytes for the 40-byte one. That is a 16-byte difference in the usable allocation size per node, not a measurement of 16 bytes of allocator overhead: what glibc spends on bookkeeping around each chunk is a separate question, and these figures are specific to this glibc version and platform; another allocator could round differently. Key copies are separate allocations and aren't affected. `pool_stats` counts objects, not bytes, and the pool's object size is `sizeof(struct rb_node)`, which already includes the pointer, so no change was needed there. We kept the pointer because it was already there since HW1 (deletion fixup depends on it) and because the alternative, Morris traversal, writes into the tree during a read-only walk.

Stress-test sizes: the spec's million-node requirement is met under AddressSanitizer/UBSan, not under valgrind. `make stress-asan` runs `test_rbtree --stress 1000000`, which builds a 10^6-node tree, balanced and as a single left spine, in both heap and pooled mode, and runs `rb_foreach` and then `rb_destroy` on a thread with a 64 KB stack. Valgrind is many times slower, so `make memcheck` routinely runs the same harness at 20,000 nodes (`--stress 20000`), and `make test`/`make asan` run that 20,000-node size too. This is a deliberate shrink for runtime, made so `make memcheck` still finishes quickly, and it is only for valgrind. The million-node case itself is not shrunk: it is opt-in behind its own target (`make stress-asan`) rather than part of `make test`, so it runs when that target is invoked, not on every build. The 20,000-node size is still big enough to catch recursion: the recursive `rb_foreach` overflowed the 64 KB stack on the 20,000-node left spine and AddressSanitizer reported it as a stack overflow in `foreach_inorder`.
