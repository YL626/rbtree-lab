**As a C newcomer,** what surprised me most was how pointers work. They look simple, since they are just `->` or `*`, but it took a while to learn how they really work. I also liked that the syntax is not too different from Java. I did not know that memory management is not as easy as calling `free()`; every allocation needs a single place where it is freed, to avoid double frees and use-after-free. I also found that some cases are simple, such as deleting a red leaf, which needs no deletion fixup.

**Pool design (Mutation 2).** Each slab is one 4096-byte `rb_malloc` block with an in-band header (just the slab-chain `next` pointer): no second allocation or failure path, at the price of header bytes. Slots are aligned to `alignof(max_align_t)` (16 here) because the pool does not know what it stores and a dead slot must also hold the free-list pointer. The header rounds up to 16, so the first slot is at offset 16, the stride is 48, and (4096 − 16) / 48 gives 85 slots with no slack; the count uses what is left after the header, not 4096. `pool_stats` reports `slabs` (slabs obtained), `live` (handed out, not yet freed) and `free_objs` (what `pool_alloc` can return without calling `rb_malloc`: free-listed plus never-carved slots), with the invariant `live + free_objs == slabs * objs_per_slab`. In debug builds `pool_stats` also walks the free list, with a bound, to cross-check its length.

**Poisoning.** `pool_free` fills the whole stride with 0xDD, then writes the free-list link at offset 0; the reverse order would overwrite the link. A freed node stays inside a live slab, so ASan treats a stale pointer into it as valid and reports nothing; poison makes a stale read see 0xDD instead of the old node. It does not detect writes to a dead slot, and poison is not verified on reuse (hostile-review gap D4). The link also occupies `key`, the first field, so a stale `key` holds the link pointer (NULL or another dead slot), not 0xDD (A2; §8.2 anticipates this). It is compiled out by `-DNDEBUG`.

**Comparison with `kmem_cache`.** Same core idea as the kernel's slab allocator (Bonwick): fixed-size objects in page-sized slabs, with a free list through dead objects. The additions below are general knowledge, not measured here. The kernel caches constructed objects, so common kinds skip re-initialisation; ours rewrites every field. Traditional slab allocators colour slabs by staggering the first slot so same-index objects avoid the same cache lines (not every modern Linux slab implementation does). Per-CPU caches let many cores allocate one kind of object without contending on a lock, which a single-threaded pool never faces. And it returns free slabs under memory pressure, because a kernel must give memory back; ours keeps every slab until `pool_destroy`, which is why whole-tree teardown never calls `pool_free`. `rb_snapshot` (COW, Mutation 4) was not attempted (optional, ungraded), so there is no COW comparison.

**Parent-pointer cost (Mutation 3).** Our O(1)-space `rb_foreach` walks parent pointers; Morris traversal was rejected because it rewrites `right` links during a read-only walk. By `sizeof` (gcc 15.2, x86-64), `struct rb_node` is 48 bytes with the pointer, 40 without. Slots round up to 16, so both give a 48-byte stride and 85 nodes per slab (measured with `rb_pool_geometry`): in pooled mode the pointer is free, by accident of layout rather than design. In ordinary mode glibc 2.43's `malloc_usable_size` reports 56 bytes for the 48-byte node and 40 for the 40-byte one; that is usable size only, not glibc's per-chunk bookkeeping, and another allocator could differ. `pool_stats` counts objects, so it needed no change. We kept the pointer because deletion fixup has depended on it since HW1.

**Testing limits.** `make stress-asan` runs 10^6 nodes, balanced and as one left spine, heap and pooled, with `rb_foreach` and `rb_destroy` on a 64 KB thread stack. The routine Valgrind gate (`make memcheck`) uses 20,000 nodes because Valgrind is much slower; that shrink is deliberate. DEVLOG records a one-off scratch Valgrind run of the full 10^6 case that was also clean, but it is not a Makefile target.

A million-node balanced-tree test alone cannot expose the recursive-stack problem; the adversarial left-spine test does. In a scratch copy (not committed), `rb_destroy` was replaced with a textbook recursive free and run under ASan. In heap mode the balanced tree passed at 20,000 and 10^6 nodes (a red-black tree's height is about 40), while the left spine, built by a test hook using the real rotations, overflowed the 64 KB stack at both sizes. The abort ended the run before the pooled cases, so the control was observed in heap mode only.
