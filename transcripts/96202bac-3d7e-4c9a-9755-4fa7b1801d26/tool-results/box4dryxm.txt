DECIDED: (1) **lazy first slab.** `pool_create` buys no slab. The decisive argument was not the saved allocation but that eager buys nothing: the "no capacity, grow" branch `pool_alloc` needs for slab 2 is the same branch it needs for slab 1, so eager would have added a second failure path and a real unwind to `pool_create` in exchange for one fewer execution of a branch that has to exist anyway. It also moves first-slab-allocation-failure to a strictly stronger test site — a `pool_alloc` that must return NULL, leave every counter untouched, and still work once the injector is disarmed, which an eager pool cannot express because its first slab can only fail at birth. Cost accepted: the empty-pool invariant assertion is vacuous (`0 + 0 == 0 * 85`) rather than merely trivial. (2) **maintained counters plus a bounded debug cross-check** (the walk lands with the free list in slice C). Option A alone was rejected on a specific ground, not a general one: with `free_objs` derived as `free_count + carve_remaining`, the headline invariant would be checked entirely against the numbers the mutators just updated, and a double `pool_free` increments `free_count` twice while decrementing `live` twice — so the sum stays consistent while the free list goes cyclic, i.e. the invariant would pass over exactly the bug the spec's M2 review prompt tells the reviewer to hunt. An on-demand walk was rejected because it makes per-op assertion quadratic under stress and, on a cyclic list, hangs instead of reporting. The bound (`slab_count * objs_per_slab + 1`) is what converts the cycle from a hang into the report. (3) **preconditions, not guarantees:** `pool_stats` and `pool_destroy` require a non-NULL pool and `pool_stats` requires all three out-parameters, asserted rather than branched on. `pool_destroy(NULL)`-safety and NULL-tolerant out-parameters were both in the proposed design and cut at review before any code existed for them — the pool is internal to one file and the assignment asks for neither, so they would have been invented API surface that later slices and the walkthrough would owe an explanation for. (4) **`pool_create` returns NULL for an `obj_size` geometry rejects**, which resolves the internal-only contract the geometry slice deliberately left open; checking the helper's boolean here means it is checked at exactly one site in the whole program. (5) `rb_pool_t` is declared **incomplete** in the test (`typedef struct rb_pool rb_pool_t;` plus three prototypes) — unlike the geometry helper's out-parameters, there is no layout to duplicate across the file boundary at all, so there is nothing that can drift.

Writing the check now anyway is still right (no scenario gets added without it), but "the invariant passes" is worth nothing until slice B gives it non-zero terms, and saying so in the log is more useful than letting a green line imply coverage it does not have. The mutation run made the same point from the other side: the one mutant the test file could not catch was the leaked pool struct, which only valgrind sees — so `make memcheck` is not a formality on this file, it is the only detector for a whole class of `pool_destroy` bug. PROOF (termination and correctness of the teardown loop): Let F be the nodes already released and R the nodes reachable from `cur` via left/right links. Loop invariant at the top of each pass: (I1) R is a binary tree rooted at `cur`, and R and F partition the original nodes; (I2) no left/right field in R points into F; (I3) R's in-order sequence is the original sequence minus F, and F is a *prefix* of it (nodes are freed in ascending key order); (I4) each node in F had its key freed once, `value_free` called once, and (heap mode) its node freed once, while nothing in R has; (I5) `t`, `value_free` and `pool` are live, while root/size/parent/color are stale and unread. A rotation keeps the node set and in-order sequence (`(A L β) cur C` = `A L (β cur C)`) and frees nothing. A free removes `cur`, which has no left child and is therefore R's minimum (so F stays a prefix) and is R's root (so nothing in R′ points to it); `next` was captured first. At exit `cur == NULL`, so R = ∅ and F is everything. **Measure:** Φ = 2N − S, with N = |R| and S = the length of the right spine from `cur`. Φ ≥ N ≥ 0 because S ≤ N. *Rotate:* N is unchanged and S grows by exactly 1 (the new spine is L, cur, then the old spine below cur), so Φ falls by exactly 1. *Free:* N falls by 1 and S falls by exactly 1 (the root was the head of the spine and the rest of the spine is `next`'s spine), so 2N falls by 2 and S by 1, and Φ falls by exactly 1. Hence the loop runs exactly Φ₀ = 2n − s₀ passes: n − s₀ rotations and n frees, linear time. Checked on an instrumented scratch copy of the real loop: iterations == 2n − s₀ with zero steps whose ΔΦ ≠ −1, for n = 1, 2, 7, 1000 and 10^5. Worked example on the perfect tree 4(2(1,3),6(5,7)), n = 7, s₀ = 3, Φ₀ = 11: rotate@4 (10), rotate@2 (9), free 1 (8), free 2 (7), rotate@4 (6), free 3 (5), free 4 (4), rotate@6 (3), free 5 (2), free 6 (1), free 7 (0). That is 4 rotations = n − s₀ and 7 frees, in ascending order.
RESULTS: Default run 3371 assertions, 0 FAIL; heap 1374 / pooled 1350, delta still 24, and all 1302 non-sweep descriptions are identical across modes (both modes grew by exactly 737: 29 new M3 assertions plus `make_int` fixture lines). `make test` ~1.9 s, `make asan` ~6.2 s, `make stress-asan` ~5.8 s (34/34 PASS at N = 10^6: foreach visited all 10^6 keys in order, 0 missed and 0 repeated destructor calls in all four cases), `make memcheck` ~6.5 s (four runs, all "All heap blocks were freed", 0 errors; the stress run did 120,484 allocs/frees). ALGORITHM: First node: descend `left` from the root; the leftmost node holds the minimum. Successor of `cur`: if `cur->right` exists, its leftmost node; otherwise climb `parent` while we arrive from a right child, and the first ancestor reached from its left side is next — reaching NULL means `cur` was the maximum and the walk ends. Loop invariant: exactly the keys < `cur->key` have been passed to `fn`, each once. Exactly-once and order follow because each step goes to the next larger key (BST order is invariant 4, which `links_ok` also checks). Termination: the number of keys greater than the last one visited starts at n − 1 and falls by one per visit; each individual step ends because descents stop at a leaf and climbs stop at the root's NULL parent (this relies on acyclic, correct parent links — the precondition T0 and `links_ok` test). Space: two `const` node pointers plus the arguments, no recursion, no allocation; `-fstack-usage` reports `rb_foreach` as a fixed (`static`) 32-byte frame at -O1/-O2 and 64 at -O0, the same as `rb_destroy`, and the only `call` in its disassembly is the indirect call to `fn`. Time: every edge is descended once and climbed once. The plan predicted 2(n − 1) pointer moves; an instrumented scratch copy measured **2n − 1** for every nonempty tree (balanced, left spine, right spine; n = 1, 2, 3, 10, 10^3, 10^5, 10^6). The extra move is the final climb from the root to its NULL parent that ends the loop, which my count had left out. An empty tree makes zero moves.

DECIDED: (1) **Parent pointers, not Morris.** Morris threading writes temporary `right` links into nodes reached through a `const rbtree_t *`. While a thread is in place, a callback's `rb_find` for an absent key between a threaded node and its successor follows the thread back down and loops forever; a callback that longjmps or exits strands the threads and leaves the tree corrupt; and every pass would write into slab memory. The parent pointer has existed since HW1 and `delete_fixup` already depends on it, so the walk adds no new trust. (2) **Callback contract** (also NOTES.md): read-only calls on the same tree are allowed, including nested traversal; `rb_insert`/`rb_delete`/`rb_destroy` on the traversed tree are undefined behaviour, with no "safe subset" promised — the successor is computed from `cur` after `fn` returns, and a two-children delete frees the *successor's* node, so even reading the successor first would not help. A callback that never returns leaves the tree valid, as a consequence of a walk that never writes, not as an extra promise. No NULL-tolerance or thread-safety claims beyond the header. (3) **No `pool_stats` change for the parent pointer's cost**: `obj_size` is `sizeof(struct rb_node)`, which already includes it, and the pool counts objects, not bytes; the byte cost is accounted for in REFLECTION.md.
LEARNED: First, the spec's "callbacks that call back in" question decided the algorithm, not just the contract: the in-between `rb_find` is exactly the read-only call Morris cannot survive, so it became a test (T2) rather than a remark. Second, the tests worth writing first were not the ones that turned red. T0–T2 were green against the recursive code and I said so rather than calling them red tests; the single discriminating test was the stress case already built in Evening 7, which is why its red run was captured verbatim. Third, an exact count is worth measuring even when the asymptotics are obvious: 2(n − 1) was wrong by one, and only the measurement showed it.
